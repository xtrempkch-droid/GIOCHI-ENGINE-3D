# Consuming GIOCHI-ENGINE from C

`docs/C_ABI_CONTRACT.md` is the specification; this page is the practical guide:
what to link, what to call first, how the error model behaves in practice, and the
rules a callback has to respect.

The header is [`giochi-engine-capi/include/giochi.h`](../giochi-engine-capi/include/giochi.h),
generated by `cbindgen` from the Rust crate. It is never edited by hand —
`scripts/gen-header.sh` regenerates it and CI fails when the committed copy is stale.

---

## 1. Build and link

```bash
cargo build -p giochi-engine-capi            # debug
cargo build -p giochi-engine-capi --release  # release
```

| Artefact | Path | Use |
|---|---|---|
| `libgiochi.so` | `target/<triple>/<profile>/` | dynamic linking (default) |
| `libgiochi.a` | same | static linking into a single executable |

```bash
cc -std=c11 -I giochi-engine-capi/include \
   giochi-engine-capi/tests/c_smoke.c \
   -L target/x86_64-unknown-linux-gnu/debug -lgiochi \
   -Wl,-rpath,'$ORIGIN' -o my_game
```

Linking statically removes the runtime dependency on `libgiochi.so`, but not on
SDL2's satellites (`libSDL2_mixer`, `libSDL2_image`, `libSDL2_ttf`) or on the KMSDRM
libraries, which SDL2 `dlopen`s — see [KMSDRM.md](KMSDRM.md) §5.

There is a complete, self-contained consumer in
[`giochi-engine-capi/tests/c_smoke.c`](../giochi-engine-capi/tests/c_smoke.c) and a
`ctypes` one in [`python_smoke.py`](../giochi-engine-capi/tests/python_smoke.py); both
run in CI via `scripts/ffi-smoke.sh`.

## 2. The five-minute program

```c
#include <stdio.h>
#include "giochi.h"

static void update(void *user_data, const GiochiTime *t) {
    (void)user_data;
    if (giochi_input_key_pressed(27 /* SDLK_ESCAPE */)) {
        giochi_engine_request_quit();
    }
    (void)t; /* t->delta is the fixed timestep */
}

static void render(void *user_data) {
    (void)user_data;
    GiochiRect bar = { .x = 10, .y = 10, .w = 120, .h = 24 };
    GiochiColor green = { .r = 40, .g = 160, .b = 90, .a = 255 };
    giochi_render_draw_rect(&bar, green);
}

int main(void) {
    GiochiEngineConfig config = {
        .width = 960, .height = 540, .target_fps = 60, .vsync = 1,
        .title = "my game",
    };
    if (giochi_engine_init(&config) != GIOCHI_ERROR_OK) {
        fprintf(stderr, "init: %s\n", giochi_get_last_error());
        return 1;
    }

    GiochiSceneCallbacks callbacks = {
        .user_data = NULL,
        .update = update,
        .render = render,
    };
    GiochiScene scene = giochi_scene_create(&callbacks);
    if (scene == 0) {
        fprintf(stderr, "scene: %s\n", giochi_get_last_error());
        giochi_engine_shutdown();
        return 1;
    }

    int32_t code = giochi_engine_run_scene(scene);

    giochi_scene_destroy(scene);
    giochi_engine_shutdown();

    if (code != GIOCHI_ERROR_OK) {
        fprintf(stderr, "run: %s\n", giochi_get_last_error());
        return 1;
    }
    return 0;
}
```

Every `_reserved` field may be omitted from the initialiser: an unmentioned field of
a C struct initialiser is zero, which is exactly what the contract requires.

## 3. Error model

* `int32_t` return: `0` = `GIOCHI_ERROR_OK`, negative = failure.
* Handles: `0` means "no handle"; the reason is in `giochi_get_last_error()`.
* **Every call clears the message on entry.** After a successful call it is `""`,
  so a stale message can never be mistaken for a new failure.
* The message pointer is owned by the library, valid until the next call on the same
  thread, and never NULL.
* `giochi_get_last_error()` is thread-local and does not touch the message.

```c
GiochiTexture t = giochi_texture_create("assets/typo.png");
if (t == 0) {
    printf("could not load: %s\n", giochi_get_last_error());
    /* asset error: failed to load texture 'assets/typo.png': Couldn't open ... */
}
```

A panic inside the library is caught at the boundary and reported as
`GIOCHI_ERROR_INTERNAL` with the panic message; it never unwinds into C.

Even a failing `void` function (for example `giochi_audio_set_volume`, which clamps
instead of failing) leaves a message when something went wrong underneath.

## 4. What may be called when

The engine is single-threaded: call everything from the thread that called
`giochi_engine_init()`. `giochi_get_last_error()` is the only exception, and it is
still per-thread.

A scene callback runs *inside* the engine's frame, so it can only use the subsystems
the engine lends it. Using anything else returns `GIOCHI_ERROR_SCENE` with a message
naming the callback it belongs in — never a crash and never silent misbehaviour.

| Callback | `giochi_render_*` / `giochi_camera_*` / `giochi_sprite_draw` | `giochi_input_*` / `giochi_gamepad_*` | `giochi_sound_*` / `giochi_music_*` / `giochi_audio_*` | `giochi_texture_*` | `giochi_asset_*` |
|---|---|---|---|---|---|
| `on_enter` | yes | — | yes | yes | yes |
| `update` | — | yes | yes | yes | yes |
| `render` | yes | — | — | yes | yes |
| `on_exit` | yes | — | yes | yes | yes |
| outside a run | yes | yes | yes | yes | yes |

The texture registry is shared rather than borrowed, which is why
`giochi_texture_create` works everywhere — including `update`, where a game may load
an asset lazily.

Engine control (`giochi_engine_init`, `run`, `run_scene`, `step`, `shutdown`) is
**not** callable from a callback. `giochi_engine_request_quit` and
`giochi_engine_is_running` are, and that is how a scene ends the loop:

```c
static void update(void *user_data, const GiochiTime *t) {
    Game *game = user_data;
    if (game->game_over) {
        giochi_engine_request_quit();
    }
}
```

`giochi_engine_is_running()` turns `0` as soon as a quit is requested, even though the
remaining fixed steps of that frame still run.

## 5. Scenes

`giochi_scene_create` copies the callback table. `user_data` and the function
pointers must stay valid until `giochi_scene_destroy`.

| Callback | When | Required |
|---|---|---|
| `on_enter` | once before the scene's first frame of this run | no |
| `on_exit` | once after the scene's last frame of this run | no |
| `update` | once per **fixed** simulation step | **yes** |
| `render` | once per display frame, after the clear and before the present | **yes** |

`update` may run zero, one or several times per `render`; a scene must not assume a
1:1 ratio. `t->delta` is the fixed timestep, not the display frame time.

`giochi_engine_run_scene` brackets exactly one `on_enter`/`on_exit` pair and leaves
the engine's scene stack empty, so the same handle can be run again — that is how a
menu → game → menu loop is written in C. `giochi_scene_destroy` while the scene is
running is an error (`GIOCHI_ERROR_SCENE`); destroying it while it is merely idle is
always safe.

`giochi_engine_run()` runs whatever is already on the stack and is what a host uses
for a "loading" screen with no scene at all: the loop runs and draws the clear colour.

## 6. Handles

* Created by `giochi_texture_create` / `_create_memory`, `giochi_sound_load`,
  `giochi_music_load`, `giochi_scene_create`.
* Destroyed by the matching `*_destroy`, which returns
  `GIOCHI_ERROR_INVALID_HANDLE` for `0`, an unknown handle, or a second destroy.
* Never reused: a stale handle can never alias a new resource.
* `giochi_texture_create` goes through the resource cache, so the same path returns
  the **same** handle and uploads once. Destroying a handle that came from the cache
  leaves a stale cache entry; the next `giochi_texture_create` for that path detects
  it and reloads (ADR-022). If several entities share a texture, destroy it once,
  when none of them need it.
* `giochi_engine_shutdown` does not free handles. Destroy them first for
  deterministic behaviour and to let the engine report leaks in the logs.

## 7. Frame pacing

Three ways to run:

```c
giochi_engine_run_scene(scene);   /* engine owns the pacing; returns when the scene quits */

giochi_engine_run();              /* same, for whatever is on the stack */

while (!done) {                   /* host owns the pacing, e.g. an editor or a test */
    if (giochi_engine_step(1.0f / 60.0f) != GIOCHI_ERROR_OK) { break; }
    /* ... */
}
```

`giochi_engine_step` never sleeps and never blocks; it polls events, runs the fixed
steps for the frame time you pass, clears, renders, presents and applies the scene
transition. A non-finite or non-positive frame time is replaced by `1/60`.

Statistics for the last run: `giochi_engine_frames`, `giochi_engine_steps`,
`giochi_engine_elapsed`, `giochi_engine_timestep`. `giochi_engine_frames` accumulates
across `step` calls.

## 8. Driving from a non-C language

Anything with `dlopen`/`LoadLibrary` can consume the same header.

* **Python** — `ctypes` needs `argtypes`/`restype` per function, as in
  [`python_smoke.py`](../giochi-engine-capi/tests/python_smoke.py). Callbacks are
  `CFUNCTYPE`, and **you must keep Python references to them** for as long as the
  scene lives, or `ctypes` will garbage-collect the trampoline the C side is holding.
* **Go** — `cgo` with the header; `//export`ed functions match the callback
  signatures directly.
* **Zig** — `@cImport` the header.
* **C#** — `DllImport` with `[StructLayout(LayoutKind.Sequential)]` mirrors of the
  structs in the header, or a generated binding.
* **Lua** — use `giochi-engine-lua`, which binds the Rust API rather than the C one
  (`docs/LUA_BINDING.md`, phase 8).

The callback table is plain C ABI: any function pointer with the right signature
works, from any language, as long as it does not unwind/throw and does not call back
into the engine's lifecycle functions.

## 9. Part II: 3D (ABI version 2)

Everything above describes part I and is unchanged. Part II adds a 3D renderer on the
same library and the same header; `giochi_abi_version()` returns `2`, and a part I
program written against `1` keeps working unchanged.

The difference that matters in practice: **the 3D engine is a pointer the caller owns**,
not a process-wide singleton. It holds a GL context, so its layout is nobody's business
(ADR-039) and every function takes or returns it explicitly.

### 9.1 The smallest complete program

```c
#include <stdio.h>
#include "giochi.h"

int main(void)
{
    GiochiEngine3D *engine = giochi_engine3d_create(NULL);   /* 1280x720 */
    if (!engine) {
        fprintf(stderr, "%s\n", giochi_get_last_error());
        return 1;
    }

    GiochiMeshHandle cube = 0;
    GiochiShaderHandle shader = 0;
    giochi_mesh_create_cube(1.0f, &cube);
    giochi_shader_builtin(GIOCHI_SHADER_PHONG, &shader);

    GiochiCamera3D camera = giochi_camera3d_new();
    GiochiVec3 eye = {0.0f, 1.6f, 2.4f, {0}};
    GiochiVec3 at  = {0.0f, 0.0f, 0.0f, {0}};
    giochi_camera3d_look_at(&camera, eye, at);

    GiochiTransform3D model = giochi_transform3d_identity();
    GiochiColor3D sky  = {0.07f, 0.09f, 0.14f, 1.0f, {0}};
    GiochiColor3D tint = {0.85f, 0.62f, 0.35f, 1.0f, {0}};

    for (int frame = 0; frame < 300; frame++) {
        giochi_engine3d_begin_frame(engine);
        giochi_renderer3d_clear(engine, sky);
        giochi_renderer3d_draw_mesh(engine, cube, shader, &model, &camera, tint);
        giochi_engine3d_end_frame(engine);
    }

    giochi_mesh_destroy(cube);
    giochi_shader_destroy(shader);
    giochi_engine3d_destroy(engine);
    return 0;
}
```

`giochi_engine3d_create(NULL)` works because the defaults are sensible; pass a
`GiochiWindowConfig` to choose a size. On KMSDRM the panel's native mode wins regardless
(ADR-035), which is why nothing in this API lets you assume the size you asked for.

### 9.2 The four functions that take no engine

`giochi_mesh_*` and `giochi_shader_*` have no engine parameter. A mesh is a GL object
belonging to the renderer that created it, so they act on the **most recently created
engine on the calling thread**. Creating a second engine on that thread is refused
(`NULL`) rather than allowed to retarget them, so there is never an ambiguity.

This mirrors part I, where `giochi_texture_create` also takes no handle. If you need
several independent scenes, render them into one engine.

### 9.3 Two traps worth naming

**A zeroed transform draws nothing.** `GiochiTransform3D t = {0};` has scale `(0,0,0)`.
Use `giochi_transform3d_identity()` or `giochi_transform3d_from_translation()`.

**An unset camera has `aspect == 0.0`, and that is correct.** It means "ask the
drawable", so the projection follows the panel. Setting it by hand is only right if you
are rendering to something that is not the window.

### 9.4 Shaders are files or built-ins, never strings

There is no function that takes GLSL source (R10, and §11 of the contract). You either
use one of the three the library ships:

| Constant | Shader | Use |
|---|---|---|
| `GIOCHI_SHADER_FLAT` | one Lambert term, no texture | coloured geometry |
| `GIOCHI_SHADER_TEXTURED` | `texture2D` plus the same term | textured geometry |
| `GIOCHI_SHADER_PHONG` | directional Blinn-Phong | a scene with light and shade |

or point `giochi_shader_load` at a `.vert`/`.frag` pair on disk. The compiler's own log
comes back through `giochi_get_last_error()`, which is the only thing that makes a shader
bug findable.

`GIOCHI_SHADER_PHONG` reads the engine's light. Until you set one, that is the built-in
sun: white, ambient 0.3, specular 0.25 at exponent 24. `giochi_renderer3d_set_light`
replaces it, and the light is **engine state** — it applies to every later frame until you
change it again, not just the next draw:

```c
GiochiDirectionalLight sun = {
    .direction = {-0.4f, -1.0f, -0.3f, {0}},  /* the way the photons travel */
    .color     = {1.0f, 0.94f, 0.82f, 1.0f, {0}},
    .ambient   = 0.25f,
    .specular  = 0.45f,
    .shininess = 32.0f,
    ._reserved = {0},
};
giochi_renderer3d_set_light(engine, &sun);
```

`direction` is normalised and `shininess` is floored at 1 for you, so a `memset`-and-forget
struct gives a dim but correct frame rather than a black one. Values above 1.0 in `color`
are legal and blow highlights out, which is how a bright sun reads.

### 9.5 Freeing things

| Created with | Freed with |
|---|---|
| `giochi_engine3d_create` | `giochi_engine3d_destroy` |
| `giochi_mesh_create_cube` / `giochi_mesh_load_obj` | `giochi_mesh_destroy` |
| `giochi_shader_builtin` / `giochi_shader_load` | `giochi_shader_destroy` |

Destroying a handle twice returns `GIOCHI_ERROR_INVALID_HANDLE`; it is not ignored, and
it is not a crash either. `giochi_engine3d_destroy` releases the GL context and the
window; handles you made become meaningless at that point, so free them first if you want
the engine to report leaks — it logs a warning when objects outlive the context.

## 10. Part III: frame statistics (ABI version 3)

Part III is one function and one struct, and it is purely additive:
`giochi_abi_version()` returns `3`, and a program written against `1` or `2` keeps
working unchanged. The contract is part III of
[C_ABI_CONTRACT.md](C_ABI_CONTRACT.md); this is the short version.

```c
GiochiFrameStats stats;
if (giochi_engine_frame_stats(&stats) == GIOCHI_OK) {
    printf("%.1f fps, %u draw calls, %.2f ms\n",
           stats.fps, stats.draw_calls, stats.frame_time_ns / 1e6);
}
```

The struct is **zeroed unless the library was built with the `profiling` feature**
(ADR-042). `stats.frames` tells the two cases apart: a measuring build counts frames, a
non-measuring one leaves it at zero. The call itself succeeds either way — "nothing has
been measured" is a state, not a failure — and it writes `out_stats` only on success, so
a failed call cannot half-update a struct that is already being displayed.

Durations are whole nanoseconds. The struct is a *projection* of the Rust `FrameStats`,
not the same type: the C surface stays narrower so that an internal measurement added to
the engine does not widen the ABI. It is 120 bytes, alignment 8, and a C program
allocates it itself — `c_smoke.c` and `python_smoke.py` assert the size and the offsets.

## 11. Verification

```bash
cargo test -p giochi-engine-capi            # unit tests + rust_ffi.rs + rust_ffi_3d.rs
scripts/gen-header.sh --check               # the committed header is current
scripts/ffi-smoke.sh                        # C and Python consumers, 2D and 3D
```

`scripts/ffi-smoke.sh` builds `libgiochi.so`, compiles `c_smoke.c` and `c_smoke_3d.c`
with `-Wall -Wextra -Werror`, runs both, then runs the two Python consumers. Part I runs
under `SDL_VIDEODRIVER=dummy`; the 3D ones force `offscreen`, because `dummy` has no
OpenGL at all, and treat exit `77` as "this machine has no Mesa" rather than a failure.
CI runs the same commands, so a change that breaks a real consumer fails the build.
