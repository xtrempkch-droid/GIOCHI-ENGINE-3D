# GIOCHI-ENGINE 3D

3D is a **parallel path**, not an extension of the 2D renderer. `giochi-engine-3d`
drives OpenGL ES through EGL; `giochi-engine` keeps using `sdl2::render`. A game picks
one. See ADR-037 for why there is no unified mode.

| Crate | Renderer | Use it for |
|---|---|---|
| `giochi-engine` | `sdl2::render` | sprites, tiles, UI, 2D games |
| `giochi-engine-3d` | GLES 2.0 via EGL | 3D scenes |

Both share window creation, input, audio and the `u64` handle discipline.

## 1. Why GLES 2.0

GLES 2.0 is the floor on the ARM64 handhelds this project targets (RK3326 class,
R35S/X35H). Their drivers are built for a fixed-function pipeline and a 2.0 shader
model; asking for 3.0 returns either an error or a context that fails on the first
draw. GLES 3.0 is available but **opt-in** — see §3.

GLSL for GLES 2.0 is `#version 100` with `precision mediump float;` in the fragment
shader. There is no `#version 300 es` in this crate (ADR-038).

## 2. How the context is created

SDL2 owns the platform surface, and EGL sits underneath it. We never call EGL
directly: `SDL_GL_CreateContext` picks the right path for whatever video driver is
active, which is what makes one binary work on a desktop and on a bare console.

The order matters, and getting it wrong is the most common mistake:

```rust
let platform = Platform::new()?;

// 1. SDL_GL_* attributes are process-global and are read when the WINDOW is created.
context::configure_attributes(&platform, GlesVersion::Gles2)?;

// 2. Only then may the window carry SDL_WINDOW_OPENGL.
let window = Window::new_opengl(&platform, WindowConfig::new(1280, 720), "3D")?;

// 3. And only then does the context exist.
let mut render = RenderContext3D::new(context::create(&window)?);
```

Setting the attributes after the window leaves you with a window that has no GL flag
and a `gl_create_context` that fails with "OpenGL support is either not configured in
SDL or not available in current SDL video driver".

## 3. Environment variables

| Variable | Effect |
|---|---|
| `GIOCHI_GL_VERSION=3` | Request a GLES 3.0 context. Anything else keeps GLES 2.0. |
| `SDL_VIDEODRIVER` | Chooses the video backend. Unset means KMSDRM when a DRM device exists. |
| `SDL_VIDEO_EGL_DRIVER` | Overrides the EGL implementation. Only needed when a vendor ships more than one. |
| `SDL_VIDEO_GL_DRIVER` | Same, for the GL library. |

`GIOCHI_GL_VERSION=3` degrades: if the driver answers with 2.0 anyway, the engine logs
a warning and continues on 2.0. It never silently pretends 3.0 features exist. Every
3.0-only path must be guarded with `render.supports_gles3()`.

### Asking for 2.0 does not always give you 2.0

Measured on a Rockchip PX30 (Mali-G31/Panfrost, Mesa 24.0.0): with
`SDL_GL_CONTEXT_MAJOR_VERSION=2` set, SDL2's KMSDRM path created an
`OpenGL ES 3.1` context anyway. It honours the *profile* request but not the
*version* request on that driver.

This matters because `supports_gles3()` is a promise about what the caller may
assume, not a report of what the driver said. A caller that asked for the 2.0 floor
must keep getting floor behaviour — otherwise a 3.0-only code path silently activates
on a request that explicitly excluded it, and it would work on the developer's desktop
and on this console but not on the device that actually needs the floor.

So the rule is: **requested 2.0 → reported 2.0, always**; requested 3.0 → reported 3.0
only if the driver's `GL_VERSION` string says `>= 3`, otherwise 2.0 with a warning.
`docs/KMSDRM.md` §8.8 records the measurement.

## 3.1 Conventions that fail silently

Three conventions are fixed in `math3d` and duplicated in `docs/C_ABI_CONTRACT.md`
§9 because each one produces a picture that looks *almost* right:

| Convention | Getting it wrong looks like |
|---|---|
| Quaternions are `(x, y, z, w)` | a camera that drifts oddly, never a visible error |
| `Transform3D` composes **scale → rotate → translate** | an object orbiting its pivot instead of rotating on it |
| Projection depth range is **-1..1** (OpenGL), not 0..1 (Vulkan) | geometry vanishing near the near plane, with no GL error |

The third one is not hypothetical. `glam` offers both `perspective_rh` (0..1) and
`perspective_rh_gl` (-1..1); the first was used initially and every matrix looked
plausible until a test asserted the NDC depth at the near plane. `math3d` uses the
`_gl` variants and `tests/math3d_integration.rs` pins the depth range.

Matrices are column-major so `Mat4::as_ptr()` can be passed to `glUniformMatrix4fv`
with `transpose = false`.

## 3.2 The camera and the drawable size

`Camera3D::aspect` of `0.0` means "unresolved", and `projection_matrix()` returns an
error rather than guessing 16:9. That is deliberate: on a console the panel is the
truth (ADR-035), and a camera that quietly assumed a wide aspect would crop a 4:3
screen with no error.

Resolve it once per frame from the renderer, which reads the real drawable:

```rust
render.begin_frame(&window);          // sets the GL viewport from window.drawable_size()
let camera = camera.with_drawable_size(
    render.drawable_size().0,
    render.drawable_size().1,
);
let view_proj = camera.view_projection()?;
```

`begin_frame` takes the window because the drawable size is a property of the window,
not of the context: KMSDRM binds the panel's native mode and ignores the requested
size, and a window can be resized. Building the viewport at construction time would
have drawn into the corner of the panel on the first console run.

## 3.3 The mesh pipeline

One interleaved vertex buffer per mesh (`position / normal / uv`), indexed with `u32`,
uploaded straight from a `#[repr(C)]` `Pod` slice with no conversion pass.

### Attribute slots are fixed, and that is load-bearing

GLES 2.0 has no `layout(location = N)` qualifier. `Program` therefore calls
`glBindAttribLocation` for `a_position`/`a_normal`/`a_uv` **before** linking, so the
slots are `0`, `1` and `2` for every program. Without that, each driver assigns whatever
index it likes per program, and one vertex array object could not serve more than one
shader.

### VAOs are optional, and both paths are tested

`glGenVertexArrays` is **core in GLES 3.0 only**. In 2.0 the equivalent lives in
`GL_OES_vertex_array_object`, and a driver may expose neither. `Mesh` holds
`Option<VertexArray>` and re-specifies the attribute pointers before every draw when
there is none.

No development machine has a driver without VAOs, so the fallback would never run before
reaching a console. `GIOCHI_FORCE_NO_VAO=1` forces it, and both CI and
`tests/mesh_pipeline.rs` draw the same cube through both paths and compare the lit pixel
count — if an offset or stride were wrong the fallback would light a different area.

```bash
GIOCHI_FORCE_NO_VAO=1 SDL_VIDEODRIVER=offscreen \
    cargo run -p giochi-engine-3d --example cube_demo -- --frames 60
```

### Shaders are files

R10: the source lives in `giochi-engine-3d/shaders/*.vert`/`*.frag` and is
`include_str!`ed for the built-ins; a user shader is loaded from a path with
`load_shader`. A compilation failure carries the driver's complete
`glGetShaderInfoLog`/`glGetProgramInfoLog` plus the source, because GLES drivers report
errors differently enough that the log is the only portable clue.

GLSL ES 1.00, `#version 100` as the first line, `precision highp float` in the vertex
shader and `precision mediump float` in the fragment shader. Tests assert all three, and
that no built-in uses 3.0-only syntax.

### Checking that it drew something

Reading pixels back is the only honest test. `tests/mesh_pipeline.rs` draws a cube and
counts non-background pixels, draws one *behind* the camera and requires zero, and the
example can capture a frame:

```bash
cargo run -p giochi-engine-3d --example cube_demo -- --frames 3 --quadro cube.bmp
```

`--quadro` reads the back buffer *before* the swap, because after `glSwapWindow` the back
buffer holds the next frame's undefined contents. Expected result for the default cube:
a solid square of roughly 313x314 pixels centred in a 1280x720 frame — measured, not
estimated.

## 3.4 Driving the camera

`CameraController` is a first-person walker: WASD to move, Q/E down and up, shift to
sprint, mouse to look. It is **not** `#[repr(C)]` and not in the C ABI — it is
interaction code, and a C consumer drives its own loop anyway.

Two design notes that matter:

* **yaw/pitch are stored as angles, not as an accumulated quaternion.** Integrating
  `orientation *= delta` every frame drifts over a long session; two clamped angles do
  not.
* **axes are decoupled from the keyboard.** `AxisInput` can come from `KeyboardState` or
  from a script. The `--auto` mode uses the second, and it exists because "playable" is
  not something a test can assert — but the direction of each axis, whether a diagonal
  is faster than a straight line, and whether the frame rate holds are all measurable.

```rust
// Interactive: real input.
controller.update(&input, mouse_delta, 1.0 / 60.0);

// Scripted: no keyboard needed.
controller.update_with_axes(
    AxisInput { forward: 1.0, strafe: 0.35, ..AxisInput::default() },
    (6.0, 0.0),   // simulated mouse movement, pixels
    1.0 / 60.0,
);
```

`set_mouse_captured` takes `Option<&MouseUtil>`: a headless run has no pointer, and
capturing the mouse must never be a requirement to start.

Measured on the PX30: 60.0 fps sustained over 300 frames with the frame cap, 57.1 fps
over 1200 uncapped, and the position walks from (0, 1.7, 8) to (38.2, 1.7, -101.0).

## 4. Troubleshooting

### "OpenGL support is either not configured in SDL or not available"

The video driver has no GL. `SDL_VIDEODRIVER=dummy` is the usual culprit — it is a
stub driver for headless 2D tests and has no EGL at all. Measured on the development
machine:

| Driver | GL available |
|---|---|
| `dummy` | **no** — this error |
| `offscreen` | **yes** — full Mesa/EGL stack, no display needed |
| `kmsdrm` | yes, when `libEGL` and `libgbm` are installed on the target |
| `x11` / `wayland` | yes |

So `SDL_VIDEODRIVER=offscreen` is how CI runs the 3D tests:

```bash
SDL_VIDEODRIVER=offscreen cargo test -p giochi-engine-3d
SDL_VIDEODRIVER=offscreen cargo run -p giochi-engine-3d --example cube_demo -- --frames 120
```

### The context fails on KMSDRM

In order of likelihood:

1. `libEGL` or `libgbm` missing from the image. Both are required; `libdrm` alone is
   not enough.
2. Another process holds DRM master. On a shipped console that is usually the
   console's own launcher — see [KMSDRM.md](KMSDRM.md) §8.1, which also documents the
   supervisor trap and the correct way to release the screen.
3. The target has no GL at all (fixed-function only). Then the 2D path is the only
   renderer available for it.

### It runs but the screen is black

`begin_frame` clears and `end_frame` presents. A window that is created correctly but
never swapped stays black forever, and the process looks healthy — this is why the
smoke example asserts `glGetError` after every frame and prints the frame count.

### VAO functions are null in GLES 2.0

Vertex array objects are **core in GLES 3.0 only**. In 2.0 they exist through
`GL_OES_vertex_array_object`, and some drivers do not expose it. Phase 11 handles this
by binding the VBO/EBO explicitly before each draw when the extension is absent, so
callers never see the difference. Check with:

```rust
render.glow().supported_extensions().contains("GL_OES_vertex_array_object")
```

## 5. Testing without a screen

Two levels, both used by CI:

```bash
# Unit tests: pure maths and layout, no driver needed.
cargo test -p giochi-engine-3d --lib

# Integration: needs a real EGL/GLES driver. Skips cleanly when there is none.
SDL_VIDEODRIVER=offscreen cargo test -p giochi-engine-3d --test context_smoke
```

The integration test reads a pixel back with `glReadPixels` and compares it to the
requested clear colour. "The call was issued" and "the surface is that colour" are
different claims, and only the second one is worth asserting.

Visual correctness — "the cube appears and spins" — is a **manual** check. It cannot be
automated without a reference image comparison, which this project does not have.
`PROGRESS.md` records when it was last done on real hardware and when it has not.
